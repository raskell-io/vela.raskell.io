What a deploy does

The old release keeps serving until the new one proves itself.

Fig. 2 The deploy sequence

  1. Upload

    The client tars your binary or BEAM release and copies it with scp. The server unpacks it into a new, read-only release directory.

  2. Start on a fresh port

    Vela runs pre_start (your migrations), then starts the new release on a random port between 10000 and 20000 with PORT and VELA_DATA_DIR set.

  3. Health check

    It asks your health path up to 30 times, a second apart. Anything but a 200 kills the new instance; the old one never noticed.

  4. Swap the proxy

    The built-in proxy points the domain at the new port and the current symlink moves. Requests in flight finish where they started.

  5. Drain the old release

    The old instance gets drain seconds, then SIGTERM, then SIGKILL. The last five releases stay on disk for vela rollback.

In the binary

The parts you would otherwise glue together.

Reverse proxy
Routes by domain, passes WebSockets through, redirects HTTP to HTTPS. Built on hyper, inside the daemon.
TLS by itself
Let's Encrypt over ACME HTTP-01, renewed 30 days before expiry. Or a Cloudflare Origin certificate, with optional mTLS for Authenticated Origin Pulls.
SSH as the control plane
The client runs scp and ssh with the keys you already have. No tokens, no deploy API to secure.
Rust and Elixir
Compiled binaries or BEAM releases. When cross-compiling is a pain, remote = true builds on the server from git archive.
Postgres and NATS
Declare them in Vela.toml. Vela installs and provisions them and injects DATABASE_URL or NATS_URL.
Secrets and rollback
Per-app secrets in a mode 0600 file, referenced as ${secret:KEY}. vela rollback goes back one release.
Backups
Scheduled copies of app data, secrets and pg_dump output, to a local path or S3. SQLite is checkpointed first.
Supervision
Restarts apps that crash and restores them when the daemon restarts. vela setup writes a hardened systemd unit.
Status and logs
vela status --json probes every health path live; vela logs my-app -f tails output from your laptop.

Your app

Four things it has to do.

  1. Listen on $PORT. Vela picks the port; read it from the environment.
  2. Answer its health path. Return 200 within 30 seconds of starting.
  3. Shut down on SIGTERM. Finish what you are doing; SIGKILL follows after a timeout.
  4. Keep files in $VELA_DATA_DIR. Databases and uploads there survive every deploy; release directories are read-only.

Scope

One server, on purpose.

Vela deploys to a single machine. It does not schedule across a cluster, and it is not trying to. If one good server runs your product, Vela is the whole platform.

Next: isolation between apps.

Apps on the same server are not yet separated by Linux namespaces or cgroups, and memory and CPU limits in [resources] are not enforced yet. Process isolation and resource limits are the next milestones. Follow along in the releases.

Your first deploy takes about ten minutes.
